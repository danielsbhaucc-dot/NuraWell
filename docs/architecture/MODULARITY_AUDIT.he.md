# ביקורת מודולריות — פלטפורמת הניהול

עודכן: 25.10.2026. המסמך מתאר איך הקוד מחולק, אילו גבולות נאכפים אוטומטית, ומה עוד פתוח.

## 1. השכבות
| שכבה | מיקום | מותר לייבא | אסור לייבא |
|---|---|---|---|
| ליבת פלטפורמה | `packages/@platform/*` (iam, qc) | ספריות npm בלבד | `apps/*`, הכינוי `@/`, Next, Supabase (ב-iam) |
| שכבות כלליות באפליקציה | `apps/web/lib/{security,ops,logs,platform,privacy,billing,monitoring,...}` | ליבת הפלטפורמה, תשתית | תחומי מוצר (ai, almog, course, journey, challenge, mentors, guides, onboarding...) |
| קוד מוצר | שאר `apps/web` | הכול | — |

## 2. מה נאכף ב-CI (חוסם מיזוג)
`npm run depcruise` רץ אוטומטית לפני `npm run test` (סקריפט `pretest`), ולכן בכל PR, וכל הכללים בחומרת **error**:
- `pkg-no-app-imports`, `pkg-no-product-alias`, `pkg-no-unresolvable`: חבילה לא יכולה להיצמד לאפליקציה.
- `platform-no-sibling-cycles`: אין מעגלי תלות בין חבילות.
- `platform-iam-pure`: מנוע ההרשאות הוא מדיניות טהורה ונבדק לבד.
- `generic-lib-no-product-domain`: שכבה כללית לא תלויה במוצר מסוים.

## 3. רישום מודולים ומוצרים
- מוצר חדש נרשם ב-`lib/platform/catalog.ts` ומקבל אוטומטית את 8 התפקידים הסטנדרטיים, דחייה כברירת מחדל ושמירה בשרת וב-RLS.
- מודול (logs, qc, ...) מוגדר פעם אחת עם הרשאות, נתיבים ומיגרציות, ומופעל לכל מוצר בנפרד (`iam_product_modules`).
- נתיב API שלא מופה נופל ל-`owner.actions`, כלומר נחסם לכולם חוץ מהמייסד.
- כל טבלת יומן נושאת `product_id` (מיגרציה 000192), כך שיומנים ובקרת איכות מסוננים לפי מוצר.
- בקרת איכות: כל מוצר רושם רשימת בדיקות (`QcCheck`) משלו; המסך גנרי.

## 4. פערים ידועים
- רוב `apps/web/lib` עדיין ספציפי ל-NuraWell; העברה הדרגתית ל-`packages/@platform/*` לפי צורך.
- `packages/billing` מנוהל בענף נפרד ולא נבדק כאן מעבר לכללי החבילות.
- בדיקת הכללים רצה על `packages` ו-`apps/web/lib`; רכיבי UI ייכנסו אחרי מעבר העיצוב למערכת העיצוב המשותפת.
