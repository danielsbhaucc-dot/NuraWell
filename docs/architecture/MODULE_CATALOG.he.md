# קטלוג מודולים ותוכנית מעבר — מוצרי SaaS רבים על אותם רכיבים

> נבנה על `feat/modular-platform-phase1` (#372). מסמך ניתוח ותוכנית בלבד: אין שינוי ב-prod ואין הרצות AI.
> סדר עדיפויות קבוע: **אבטחה → פרטיות → פיצ'רים**. **אסור שאיכות אלמוג תיפגע.**

## 0. החזון
כמה מוצרים, לכל אחד עיצוב משלו (שמעוצב יחד עם דניאל), על אותם רכיבים, ומחליפים רק הגדרות:
- רישום שמתחבר למסד אחר
- ליווי שבו רק הנושא מתחלף
- מערכת קורסים מוכנה
- רכיב נגישות שבו רק העיצוב משתנה

## 2. מודולים חסרים
1. **מערכת קורסים כללית (LMS):** יש בסיס (`courses`, `lessons`, `lesson_progress`, נגן, PDF, שקופיות), אבל הוא קשור למסע, לאלמוג ולמעקב משקל. חסרים:
   - מודל כללי: קורס → פרקים → שיעורים → תרגילים
   - בחנים ותעודות
   - הרשמה לפי מוצר והרשאות גישה (הכללה של `guide_access_grants`)
   - עורך תוכן ב-Ops
   - התקדמות שלא תלויה במשימות
   **מאמץ:** L, בשני שלבים: קודם חילוץ לקריאה בלבד, ואז הרחבה.
2. **תבניות מייל לכל מוצר:** שולח, לוגו וצבעים.
3. **הגדרות מוצר בזמן ריצה:** טעינת המניפסט לפי דומיין.
4. **ערכת עיצוב לכל מוצר:** היום יש פלטה אחת בלבד.
5. **אנליטיקה לכל מוצר:** משפך והחזקה, בלי פרטים מזהים.
6. **מסמכים משפטיים בתבנית:** מדיניות פרטיות ותנאים שממולאים מהמניפסט, ונבדקים משפטית לכל מוצר.

## 3. עיצוב לכל מוצר (`@platform/ui`)
- **`ProductTheme`**:
  - `palette`: סולם primary/accent/ink בגוונים 50–950
  - `surfaces`: רקע, כרטיס, זכוכית, ו-Ops
  - `fonts`: כותרת וגוף, עם פונטים עבריים ברישיון שמאפשר שימוש מסחרי
  - `radius`, `shadow`, `motion`
  - `logo`
- **`defineTheme(theme)`**: מאמת חוקים בזמן build ובבדיקה, ונכשל אם מופר חוק:
  - אין `#fff`/`#ffffff`/`white` ברקעים או במשטחים (בהרחבה של `isPureWhite` הקיימת)
  - אין גרדיאנט צהוב→ירוק: בדיקת גוון של זוגות `gradient` (hue 45–70 → 90–160)
  - אין משטח שטוח בקרם/מנטה: משטח בגוון קרם/מנטה בהיר חייב עומק (גרדיאנט, זכוכית או טקסטורה), ולא צבע אחיד
  - ניגודיות AA לטקסט ולכפתורים
- **`tokensCss(theme)`**: מייצר את אותם `--color-*`, כך שהקומפוננטות לא משתנות, ורק המשתנים מתחלפים.
- **`nurawellTheme`**: הערכים של היום, אחד לאחד. בדיקת snapshot מוודאת שה-CSS שנוצר זהה ל-`globals.css`.
- **קבוע בכל ערכה:** `dir="rtl"`, mobile-first, אותם רכיבים (קווי ההפרדה במובייל לא משתנים).
- **רכיב הנגישות** מקבל `theme` ומשתמש רק במשתני CSS. **ההתנהגות לא נוגעת**, ונבדקת בבדיקות התנהגות קיימות ובצילומי מסך.
- **הערה:** ערכה חדשה מעוצבת יחד עם דניאל, ונבדקת מול המוצר הקנוני ודף הנחיתה.

## 4. חוזה המוצר (Product Manifest)
```ts
// packages/@platform/product/src/manifest.ts
export interface ProductManifest {
  id: string;                 // 'nurawell' — תואם platform_product_registry.id
  displayName: string;        // שם מוצר בעברית
  domains: string[];          // לטעינה לפי host
  locale: 'he' | 'en';  dir: 'rtl' | 'ltr';
  theme: ProductTheme;        // @platform/ui
  db: { urlEnv: string; anonKeyEnv: string; serviceKeyEnv: string }; // שמות משתנים בלבד, אף פעם לא סודות
  encryption: { keyPurpose: string };          // field:<id>
  modules: {
    auth: { providers: ('email'|'google')[]; onboarding?: string };
    coaching?: { topicPack: string; persona: { name: string; avatar: string } };
    courses?: { enabled: boolean };
    notifications?: { channels: ('push'|'email')[]; quietHours: [string,string] };
    billing?: { plans: string };
    a11y: { enabled: true };   // תמיד פעיל, רק עיצוב משתנה
    legal: { entity: string; healthData: boolean };
  };
  copy: Record<string, string>; // טקסטים מערכתיים
}
```
- המניפסט נשמר בקוד, ב-`products/<id>/manifest.ts`, ועובר review.
- `platform_product_registry` מקבל עמודות `manifest_version`, `modules jsonb`, `theme_id` (מיגרציה חדשה; בלי סודות). סקריפט CI מסנכרן ובודק התאמה בין הקוד ל-registry.
- `/ops/products` מציג לכל מוצר: מודולים פעילים, דוגמית צבעים, נושא הליווי, גרסת המניפסט, סטטוס סנכרון, ואת המדדים הקיימים.
- **פרויקט מסד נפרד לכל מוצר:** ברירת המחדל היא מסד משותף עם `product_id` ו-RLS (שלב 5 ב-MODULAR_PLATFORM). פרויקט נפרד דורש החלטה של דניאל, כי בלי Supabase Pro יש מגבלת פרויקטים חינמיים.

## 5. אילוץ קשיח: אלמוג לא משתנה
- **רק refactor ששומר התנהגות.** לפני כל הזזה:
  1. **בדיקות זהב:** מקליטים את הפרומפט המלא (system, הודעות, כלים ופרמטרי מודל) שהקוד הקיים בונה לכ-30 תרחישים קבועים: קליטה, צ'אט רגיל, SOS, התראה, סיכומים יומי, שבועי וחודשי, ו-QC. ההקלטה דטרמיניסטית: שעון קבוע, ספק בדיקה, בלי קריאות AI.
  2. אחרי ההזזה, הבדיקה משווה **byte-for-byte**. כל הבדל מכשיל את ה-CI.
  3. **פלט:** בונים מחדש פלט של מודל מוקלט (fixtures), ובודקים שה-parse, ה-sanitize וה-QC נותנים תוצאה זהה.
  4. גם הניתוב (Luna/Terra) ומבנה המטמון (cache_control) נבדקים כחלק מהבקשה.
- אין שינוי במודלים, בפרמטרים או בטקסט. אין השוואות מודלים חדשות. אין עלות AI.
- **נגישות:** רק משתני צבע ופונט. אין שינוי ב-DOM, בקיצורים, ב-ARIA או בשמירת העדפות. בדיקת DOM snapshot לפני ואחרי.

## 9. כל פיצ'ר לוקחים, כמו תוסף WordPress
### 9.1 מלאי
**כלל:** כל פיצ'ר ב-NuraWell ממופה למודול, או מסומן "להפוך למודול". הקובץ `modules/INVENTORY.md` נוצר מ-`app/*`, `components/*`, `lib/*` ו-`app/api/*`, ו-CI נכשל על תיקייה שלא ממופה.
- **מוכן או כמעט:**
  - שכבות האבטחה (סעיף 8)
  - ui
  - ai-engine
  - auth
  - billing
  - נגישות
  - ops-products
  - qc
- **להפוך למודול:**
  - **ליבת אלמוג ותוכן:**
    - אלמוג (chat, memory, summaries, insights, mentorship)
    - מסע ותוכנית (journey, orchestrator, plans)
    - משימות והרגלים (tasks, action-hub, challenge)
    - קורסים ומדריכים (course, guides, lessons, media, media-manager, audio/tts)
    - התקדמות ודוחות (progress, progress-report, weight)
  - **חוויית משתמש:**
    - קליטה (onboarding)
    - פרופיל והגדרות
    - בית (home)
  - **תקשורת ותשלום:**
    - התראות ו-push
    - מייל
    - תמחור ותשלומים
  - **ניהול ותפעול:**
    - ops, admin ולוגים
    - Gideon (סריקת אבטחה)
    - ניטור ו-churn
  - **ציבורי ובטיחות:**
    - דף נחיתה, coming-soon, demo-access ודפים ציבוריים
    - בטיחות/SOS
  - **מודולים חוצי-מערכת:** i18n, workflows, cdn ו-storage

### 9.2 מבנה מודול (כל מודול, כולל מודולים קיימים)
```
packages/<scope>/<name>/
  module.json      # id, version, description, provides{routes,apis,jobs,ui,tables}, requires{modules:{id:semver}}, env[] (שמות), migrations[], conformance[], toggleable, dataPolicy
  README.he.md     # מטרה, API ציבורי, הגדרות, env (שמות), מיגרציות, בדיקות, התקנה במוצר חדש, איך תורמים חזרה
  CHANGELOG.md     # semver
  src/  migrations/  tests/  conformance/
```
- **`AGENTS.md` בשורש**, ש-agent קורא ראשון:
  - מפנה ל-`modules/INDEX.md`, שנוצר אוטומטית מקובצי `module.json`
  - כללי עבודה: אבטחה קודם, בלי סודות, ובלי לשנות את אלמוג
  - הפקודות: `modules list`, `check`, `install` ו-`pack`

### 9.3 גרסאות ושיתוף בין ריפוזיטוריז, בלי שירות בתשלום
- **semver לכל מודול:**
  - כל מודול מחזיק `CHANGELOG.md`
  - שינוי שובר מחייב major
  - תיוג git בצורה `mod/<name>@x.y.z`
- **הפצה:** כולל GitHub Packages (npm) בריפו פרטי, שהוא חינם לשימוש פנימי בגבולות. גיבוי: `npm pack` ל-tarball שמצורף ל-GitHub Release, ומותקן לפי URL. אין registry בתשלום.
- **"קח מודול" לפרויקט אחר:** `node scripts/modules/install.mjs <id> --target <repo>`. הפקודה:
  - מתקינה את החבילה בגרסה נעולה
  - מעתיקה את המיגרציות לתיקיית המיגרציות של היעד, בקידומת `mod_<id>_`
  - מוסיפה רשומה ל-manifest
  - מדפיסה את שמות ה-env החסרים
- **"החזר מודול" (contribute back):** מודול שנבנה בפרויקט אחר עובר לריפו NuraWell (או לריפו `platform-modules` נפרד, אם יגדל) כ-PR. הוא חייב:
  - module.json תקין
  - README
  - בדיקות התאמה ירוקות
  - review אבטחה של Gideon, עם הממצאים לאורי
  
  אחרי המיזוג הוא ניתן ל-install בכל מוצר.

### 9.4 מיגרציות לכל מודול ולפרויקט Supabase אחר
- **כתיבה:** כל מודול מחזיק את המיגרציות שלו, עם schema-qualified names ובלי תלות ב-ID של פרויקט. הן אידמפוטנטיות (`if not exists`), ובראש כל אחת יש `-- requires: mod_x@>=1`.
- **רישום:** הטבלה `platform_module_migrations(product_id, module_id, version, applied_at, checksum)` מתעדת מה הוחל.
- **התקנה בפרויקט אחר:** `modules migrate --project <ref>` מריץ לפי סדר התלויות.
- **NuraWell:** מקבל baseline שמסמן את המיגרציות הקיימות כ"הוחלו", בלי להריץ אותן מחדש.
- **הסרה:** מיגרציית down רק לאובייקטים ריקים. טבלאות עם נתונים מועברות לארכיון (rename ל-`archived_*`), ולא נמחקות.

### 9.5 בדיקות התאמה (conformance) — כל מוצר חייב לעבור
**בדיקות החובה:**
1. אין טקסט גלוי בעמודות שמסווגות כרגישות. כל ערך מתחיל ב-`enc:v2:`.
2. כתיבה של טקסט גלוי לעמודה רגישה נדחית (הטריגר פעיל).
3. Ops נכשל סגור:
   - 404 למי שאינו אדמין
   - 404 בלי מכשיר מאושר
   - 404 בלי step-up לפעולה רגישה
4. RLS: משתמש א' לא קורא נתונים של ב', ומוצר א' לא רואה מוצר ב'.
5. מסנן מידע מזהה רץ לפני כל קריאת AI. נבדק על קורפוס בדיקה, דרך ספק בדיקה, בלי עלות.
6. אין הסכמה, אין עיבוד מידע בריאותי.
7. כל פעולת אדמין נכתבת ל-audit.
8. מודול כבוי מחזיר 404, וה-jobs שלו לא רצים.
9. אין סודות בקוד ואין `#fff` ברקעים.

**איך זה רץ:**
- הבדיקות רצות ב-CI של כל מוצר דרך `@platform/conformance`.
- בדיקות 1–2 רצות גם מול prod, כבדיקה לילית לקריאה בלבד.

## 10. מחזור חיים של מודול והפעלה בקליק
- **מצבים:** `available → installed → enabled ⇄ disabled → uninstalled`.
- **טבלה:** `platform_product_modules(product_id, module_id, version, state, config jsonb, updated_by, updated_at)`.
- **אכיפה בשרת (לא רק UI):**
  - `proxy.ts` וכל route handler עוברים דרך `requireModule(productId, moduleId)`. מודול כבוי מחזיר 404 שקט.
  - ה-cron וה-jobs בודקים את מצב המודול לפני ריצה.
  - ה-UI מסתיר.
  - ברירת המחדל במקרה של שגיאה: **כבוי** (fail closed). יוצאים מהכלל מודולי האבטחה, שהם **תמיד פעילים** ולא ניתנים לכיבוי.
- **תלויות:**
  - `requires` ב-module.json
  - אי אפשר להפעיל מודול לפני התלויות שלו
  - אי אפשר לכבות מודול שאחר פעיל תלוי בו; מוצגת הרשימה
  - מעגלים נחסמים ב-CI
- **התקנה:**
  - בקוד: CLI (`modules install`)
  - במוצר: `/ops/products/<id>` עם מתג לכל מודול, גרסה, תלויות, ו-env חסרים (שמות בלבד)
- **הסרה:** מכבה ומסמן uninstalled. **נתוני משתמשים לא נמחקים.** טבלאות עוברות לארכיון, ומחיקה בפועל רק אחרי אישור מפורש של דניאל, דרך כרטיס.
- **אבטחת המתג:**
  - הרשאת IAM `modules.manage` על המוצר
  - step-up טרי (passkey) לכל שינוי
  - רישום ל-audit: לפני ואחרי, מי ומאיזה מכשיר
  - הגבלת קצב
  - אישור בדיאלוג מעוצב, לא alert של הדפדפן
  - כיבוי של מודול עם נתונים מציג כמה רשומות יושפעו
  - ברירת מחדל למוצר חדש: רק מודולי אבטחה, auth ו-ui פעילים

## 11. אימוץ קל ומאובטח: פקודה אחת, שורה אחת
- **פקודה אחת:** `npx @platform/modules add <id>`. היא:
  - מתקינה את החבילה
  - מעתיקה את המיגרציות
  - מוסיפה **שורה אחת** למניפסט: `modules: { '<id>': { enabled: true } }`
  - מריצה בדיקה
- **הגדרה שחסרה = כשל סגור:** חסר env או מפתח, המודול לא עולה ומחזיר 404 או שגיאה מפורשת בלוג, ולעולם לא רץ "פתוח".
- **בדיקת אימוץ ב-CI:** `modules verify`. היא:
  - מריצה את בדיקות ההתאמה (9.5) של כל מודול פעיל
  - בודקת שכל ה-env קיימים (שמות בלבד)
  - בודקת שהמיגרציות הוחלו
  - בודקת שמודול כבוי מחזיר 404
  
  PR שמוסיף מודול ונכשל בבדיקה לא נכנס.
- **בקנה מידה:** תוכנן ל-10+ מוצרים:
  - רישום מודולים מרכזי (`modules/INDEX.md` + registry)
  - מסך "מודולים × מוצרים" ב-/ops/products: מטריצה עם גרסה ומצב בכל תא, והתראה על מודול בגרסה ישנה

## 12. דרגות הפצה: פנימי / ניתן לשיתוף / ניתן למכירה
כל `module.json` מצהיר `distribution: "internal" | "shareable" | "sellable"`.
| דרגה | משמעות | דרישות |
|---|---|---|
| internal | רק למוצרים של דניאל | README, בדיקות, התאמה |
| shareable | אפשר לתת לאחר (קוד או חבילה) | + אין תלות בסודות או במסד של NuraWell, + רישיון מוגדר, + תיעוד חיצוני |
| sellable | מוצר עצמאי ללקוחות | + אריזה עצמאית, + רישיונות לקוח, + אבטחת לקוחות חיצוניים (12.3), + גרסאות חתומות |

**מיפוי ראשוני:**
- **sellable:**
  - רכיב נגישות, שהוא **המועמד הראשון**
  - ייתכן בהמשך: מסנן PII לפני AI, ומודול הסכמות וראיות משפטיות
- **shareable:**
  - ui
  - security-crypto
  - data-classification
  - audit
  - conformance
- **internal:**
  - אלמוג (ליבה + topic packs)
  - IAM/Ops
  - שאר המודולים
  
  אפשר לשדרג דרגה בהחלטה של דניאל.

### 12.1 אריזה עצמאית למודול sellable
- **חבילת npm** עצמאית: אפס ייבוא מ-apps/*, אפס משתני NuraWell, וכל התלויות מוזרקות.
- **ווידג'ט, ובראשו הנגישות:** קוד הטמעה בשורה אחת:
  `<script src="https://<cdn>/a11y/v1.js" data-key="pk_live_…" defer></script>`
  - **מפתח רישיון לכל לקוח:** ציבורי, בלי סוד. הוא מזהה את הלקוח בלבד.
  - **רשימת דומיינים מותרים לכל מפתח:** נבדקת בשרת לפי Origin/Referer. על דומיין לא מורשה הווידג'ט לא נטען (fail closed).
  - **הגדרות multi-tenant:** ערכת עיצוב, שפה, מיקום ומודולים פעילים, לפי מפתח, מטבלת `widget_tenants` **בפרויקט נפרד** משלו ולא במסד של NuraWell.
  - **מדידת שימוש:** טעינות ופתיחות לפי מפתח ויום, מצטבר בלבד, בלי IP שמור ובלי מזהה משתמש.
- **בלי תלות:** אפס תלות בסודות או במסד של NuraWell. גם בתוך NuraWell הווידג'ט רץ דרך אותה חבילה, ולכן הוא משמש בדיקת-אמת למוצר הנמכר.
- **הנגישות:** **ההתנהגות לא משתנה** עד שדניאל יסביר. בשלב הזה רק עוטפים, מוסיפים theme וטוענים בשורה אחת. בדיקת DOM snapshot ובדיקת התנהגות זהות לפני ואחרי.
- **הערה:** הצהרת נגישות ותאימות לתקן (ת"י 5568 / WCAG) היא אחריות האתר המטמיע. נדרש ניסוח משפטי, ראו 12.2.

### 12.2 רישיון ותנאים מסחריים: ממתין להחלטת דניאל
- **רישיון:** `LICENSE` למודול. לבחור בין קנייני, MIT או dual.
- **מחיר:** ___ ₪ לחודש/שנה לדומיין, תוכנית חינמית כן/לא, וגבול שימוש ___.
- **סליקה:** ממתינה לבחירת סולק.
- **מע"מ וחשבוניות:** ממתין להחלטה.
- **תנאי שימוש ללקוח:** כולל הגבלת אחריות, הבהרה שהווידג'ט לא מבטיח עמידה מלאה בתקן, ו-SLA.
- **DPA:** רק אם נאסף מידע אישי. כברירת מחדל לא נאסף.
- **תמיכה ועדכונים:** ___.

### 12.3 אבטחה ללקוחות חיצוניים
- **בידוד לקוחות:** כל שורה לפי `tenant_id`, RLS, ומפתח שלא ניתן לנחש. אין גישה חוצה לקוחות, וזה נבדק בבדיקת התאמה.
- **אין PII כברירת מחדל:** הווידג'ט לא שולח טקסט מהדף, ולא כותב cookies מזהים (רק localStorage להעדפות). כל שליחת מידע היא opt-in ומתועדת.
- **גרסאות חתומות:**
  - חתימה: npm provenance וחתימת Sigstore (cosign) דרך GitHub Actions, בחינם
  - SRI hash לקובץ ההטמעה
  - גרסה נעולה (`v1.4.2.js`) לצד `v1.js`
- **SBOM:** CycloneDX לכל גרסה (`npm sbom`), מצורף ל-Release.
- **פגיעויות:**
  - הודעות דרך GitHub Security Advisories
  - `SECURITY.md` עם כתובת לדיווח
  - חלון תיקון מוגדר
  - Dependabot
- **הקשחה:**
  - CSP-friendly: אין `eval` ואין inline
  - Shadow DOM לבידוד
  - הגבלת קצב לכל מפתח
  - מפתח שדלף ניתן לביטול ולהחלפה מ-Ops, עם step-up ו-audit

## 13. תיעוד לבני אדם ול-agents
לכל מודול:
- **`README.he.md` ו-`README.md`** (לבני אדם): מטרה, API ציבורי, הגדרות, שמות env, מיגרציות, בדיקות, התקנה, ואיך תורמים חזרה
- **`llms.txt`** (ל-agents): תקציר של 30–60 שורות, שכולל:
  - מה המודול עושה
  - פקודת ההתקנה
  - השורה במניפסט
  - חתימות ה-API
  - מה אסור לשנות (למשל התנהגות הנגישות)
  - איך לבדוק
- **`examples/`**: אינטגרציה מינימלית שרצה

בשורש:
- `AGENTS.md`, `llms.txt` (אינדקס לכל המודולים) ו-`modules/INDEX.md`
- כולם נוצרים אוטומטית מ-`module.json`, ו-CI נכשל אם הם לא מעודכנים

**מטרה:** agent חדש, ב-Cursor או בכל כלי אחר, מבין, מתקין ומאמת מודול תוך דקות.
